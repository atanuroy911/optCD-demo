# Controlled experiments E1 (Q1) and E2 (Q2)

Both are paired runs on real-world workflows: two variants of the same job,
identical except for one factor, run through OptCD on real GitHub Actions.
All workflows are in `workflows/`, raw run data in `data/raw/`, console
logs in `logs/`.

Token note: the `.env` PAT is currently rejected by GitHub ("Bad
credentials"), so runs used `GITHUB_API_TOKEN=$(gh auth token)`.

---

## E1: does an orphan upload alone change OptCD's verdict? (Q1)

**Project:** `stleary/JSON-java` (in the paper's population; its real
workflow uploads three artifacts per job that nothing downloads).

**Variants** (`workflows/E1-json-java/`), both copied from the real
`pipeline.yml` job `build-17`:

| Variant | File | Difference |
|---|---|---|
| with-upload | `e1-with-upload.yml` | job verbatim, incl. 3 `upload-artifact` steps |
| no-upload | `e1-no-upload.yml` | same job minus those 3 steps (the only diff) |

**Runs:**

| Variant | Detection run | Raw data | Console |
|---|---|---|---|
| with-upload | `37208714988` | `data/raw/JSON-java-37208714988/` | `logs/E1-with-upload-console.log` |
| no-upload | `37209308766` | `data/raw/JSON-java-37209308766/` | `logs/E1-no-upload-console.log` |

Both were stopped after detection; the fixer stage is not needed for Q1.

### Who reads `target/site/`

Script: `scripts/access_by_step.py`. Logs: `logs/access_by_step_E1-with-upload.log`,
`logs/access_by_step_E1-no-upload.log`. Every raw file event under
`target/site/` is mapped to the workflow step running at that moment.

| Variant | Reads of `target/site/` | During which step |
|---|---|---|
| with-upload | **15** | all inside **"Upload Test Report 17"** (`upload-artifact`), one 22 ms burst |
| no-upload | **0** | none |

`target/site/` is generated by `mvn site` in "Build Test Report" and is not
read by anything else in the job. The upload step is its only reader.

### What OptCD flags (`logs/E1_flagged_comparison.log`)

| Unused dir reported | with-upload | no-upload |
|---|---|---|
| `target/site/css/` | not flagged | **flagged** |
| `target/reports/{css,fonts,images/...}` | flagged | |
| `target/reports/{css,js,img}` | | flagged |
| `target/javadoc-bundle-options/` | flagged | flagged |
| `target/maven-status/.../testCompile/default-testCompile/` | flagged | flagged |
| `target/maven-status/.../compile/default-compile/` | flagged | |
| `target/classes/META-INF/` | flagged | flagged |
| `.git/hooks/` | flagged | flagged |

**Result.** Removing the three upload steps, with nothing else changed,
turns `target/site/` content from "used" into "unused". The upload's own
read was the only thing hiding it. This is the `000-research/`
Experiment 2 mechanism, reproduced on a real project's real workflow, and
it matches the paper-data observation that JSON-java's uploaded dirs are
never flagged (`evidence/q1_artifacts.md`).

### Caveats seen in the data

- **Only `site/css/` is flagged, not all of `site/`.** The watcher recorded
  15 reads of `site/` files in the with-upload run but only 4 creates. It
  misses creations inside freshly made subdirectories (the "recursive
  watching" race OptCD's README warns about). Files whose creation is
  missed can never be classified unused, so the flagged set is a lower
  bound.
- **Run-to-run variation.** The flagged `target/reports/` subfolders differ
  between the variants (`fonts`, `images` vs `js`, `img`), although the step
  that writes them is identical. Same instability as `maven-status` (Q3):
  OptCD's output for an unchanged step is not deterministic.
- **The jar is a confounded case.** `target/json-*.jar` is re-read by
  Maven's own packaging in both variants, so it looks used either way.
  This is the self-access confound from `000-research/` §4b.
- **`surefire-reports` is not an upload-only case here.** It has a genuine
  in-job reader (`mvn surefire-report:report-only`), so it is correctly
  "used" in both variants.

## E2: do parallel builds break plugin attribution? (Q2, H1)

**Project:** `google/gson` (6-module reactor).

**Variants** (`workflows/E2-gson/`), both from the real `build.yml` job
`build`, pinned to JDK 17:

| Variant | Maven command |
|---|---|
| sequential | `mvn verify javadoc:jar` |
| parallel | `mvn -T 4 verify javadoc:jar` (the only diff) |

**Runs:**

| Variant | Detection run | Raw data |
|---|---|---|
| sequential | `37208820120` | `data/raw/gson-37208820120/` |
| parallel | `37209217089` | `data/raw/gson-37209217089/` |

**Test.** `scripts/q2_timing_and_mapper_compare.py` applies the paper's
attribution rule (pick the plugin whose `[INFO] --- ... ---` log line came
most recently before the file event) to the first file event in each
goal's exclusive output directory. It uses raw events, so neither mapper
implementation is involved. Results:
`results/q2_timing_and_compare_gson-37208820120.json`,
`results/q2_timing_and_compare_gson-37209217089.json`,
`logs/E2_surefire_picks.log`.

| True producer | Sequential correct | Parallel (`-T 4`) correct |
|---|---|---|
| `surefire:test` (`surefire-reports/`) | **5 / 5** | **1 / 5** |
| `compiler:compile` (`maven-status/.../compile/`) | 1 / 6 | 0 / 6 |
| `compiler:testCompile` (`maven-status/.../testCompile/`) | 0 / 6 | 0 / 6 |

Every wrong `surefire` pick in the parallel run blames a plugin from a
**different module**:

| Module whose `surefire-reports/` it is | Sequential picks | Parallel picks |
|---|---|---|
| gson | `surefire:test @ gson` | `surefire:test @ gson` |
| test-jpms | `surefire:test @ test-jpms` | `proguard:proguard @ test-shrinker` |
| test-graal-native-image | `surefire:test @ test-graal-native-image` | `spotless:check @ test-jpms` |
| gson-extras | `surefire:test @ gson-extras` | `proguard:proguard @ test-shrinker` |
| proto | `surefire:test @ proto` | `exec:java (r8) @ test-shrinker` |

**Result.** With the project, commit and job held fixed, adding `-T 4`
alone drops `surefire` attribution from 5/5 to 1/5, and every error is
cross-module. That is the same signature as seata in the paper's data (47
cross-module errors, all in `-T 4C` builds), so H1 no longer rests on a
single repo. `surefire-reports` is the directory type OptCD flags most
often, and the Fixer builds its Gemini prompt around the blamed plugin.
Under parallel builds the prompt would name a plugin from the wrong module.

`maven-status` is wrong in both variants: that is boundary fragility (H3),
independent of parallelism.
