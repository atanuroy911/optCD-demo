# Side finding: step attribution breaks when any path contains "optcd"

Found while verifying E1 (JSON-java). It affects which *workflow step*, and
therefore which **command**, a directory is blamed on, and so which command
Gemini is asked to rewrite. It is separate from plugin attribution (Q2).

## How OptCD finds the responsible step

The Logger inserts `touch optcd-N.txt` after every original step
(`logger/utils.py`). The mapper then counts how many such marker files were
created before an unused directory, and uses that count as the step index
(`mapper/utils.py`):

```python
for file, timestamp in timestamps.items():
    if "optcd" in file:                      # mapper/utils.py:26, unchanged from the paper
        dummy_file_timestamps.append(parser.isoparse(timestamp))
...
j = bisect_right(dummy_file_timestamps, timestamp)   # step index
```

The marker test is a substring match on the **whole path**. Any other
created-and-never-read file whose path contains `optcd` becomes an extra
marker and shifts every step index after it.

## What triggered it here

The fork branch used for all our runs is named `optcd-run`. At checkout,
git briefly creates the ref lock file `.git/refs/heads/optcd-run.lock`,
which the watcher records:

```
2026-10-04T14:17:47.627519Z;/home/runner/work/JSON-java/JSON-java/.git/refs/heads;optcd-run.lock;IN_CREATE
```

(`data/raw/JSON-java-37208714988/inotify/.../inotifywait-log-build-17 (17).csv`).
It is never read again, so it stays in the timestamps dict and is counted
as a marker before `optcd-3.txt`. The same file appears in all 8 jobs of
the September gson run (`data/raw/gson-33849635845/`).

## Effect (E1 with-upload run, verified)

`target/reports/` (surefire-report HTML, generated by `mvn surefire-report:report-only`
in step 4 "Build Test Report") was created at 14:18:19.997-14:18:20.507,
between the markers `optcd-6.txt` (14:18:13.716) and `optcd-7.txt` (14:18:27.901).

| | Markers counted before 14:18:19.997 | Step index | Step blamed |
|---|---|---|---|
| Correct (real markers only) | 4 | 4 | Build Test Report |
| OptCD (lock file counted too) | **5** | **5** | **Upload Test Results** (`actions/upload-artifact@v5`) |

Consequence, visible live in `logs/E1-with-upload-console.log`: the fixer
asked Gemini to rewrite the "command" `actions/upload-artifact@v5` (an
action reference, not a shell command) to stop generating `target/reports/`.

## Correction to `000-research/`

`000-research/` bug 6 ("off-by-one in step attribution ... crashes with
IndexError ... fixed by clamping") misdiagnosed this. The `IndexError` was
the spurious lock-file marker pushing the index past the last step. The
clamp hid it: such directories were silently mapped to the job's last
original step, which happened to look right for jsoup (whose Maven step is
the last step). Root cause is the substring marker test, triggered by our
branch name.

## Scope and fairness

- Triggered by our setup choice (branch `optcd-run`). The paper's own
  forks lived under an `experiment-optcd` account (owner field in
  `eval/fixer/updated_prompt_result.json`); whether their runs hit this
  depends on branch and path names we cannot see.
- The fragility is real, though: OptCD's README tells users to "switch to a
  convenient branch", and a branch, directory or file name containing
  `optcd` silently shifts every step attribution.
- Q1 classification (used/unused) does not use step attribution, so E1's
  Q1 result is unaffected. E2 tests plugin attribution with the paper's
  nearest-log-line rule on raw file events, which also does not use the
  markers.
